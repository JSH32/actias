None of this is needed to build on Actias. It explains how the platform
behaves under load, for readers who want the mechanics behind the
promises in [guarantees](/docs/runtime/guarantees).

## Services

<table>
  <thead>
    <tr><th>Service</th><th>Stores</th><th>Role</th></tr>
  </thead>
  <tbody>
    <tr><td>worker</td><td>SQLite per object, local caches</td><td>runs scripts, hosts objects, serves HTTP and the node-to-node data plane</td></tr>
    <tr><td>script service</td><td>Postgres, Redis, blob storage</td><td>scripts and revisions, the placement store, live dev sessions</td></tr>
    <tr><td>kv service</td><td>Postgres by default; ScyllaDB selectable</td><td>typed key-value pairs by project and namespace</td></tr>
    <tr><td>secret service</td><td>Postgres</td><td>envelope-encrypted secrets; workers hold no key material</td></tr>
    <tr><td>api</td><td>Postgres</td><td>public REST gateway: auth, projects, access control</td></tr>
  </tbody>
</table>

Services speak gRPC to each other. Workers also speak gRPC among
themselves: forwarded object calls, delivery batches, directory hops
and holder reads travel node to node without a coordinator. Replicas
come from blob storage, not from a peer.

```mermaid
flowchart LR
    client([Client]) --> w1
    subgraph workers[worker nodes]
        w1[worker 1] <--> w2[worker 2]
    end
    w1 --> ss[script service]
    w1 --> kv[kv service]
    w1 --> sec[secret service]
    w1 --> blob[(blob storage)]
    api[api gateway] --> ss
    api --> kv
    dash([Dashboard / CLI]) --> api
```

The api is the control plane: it never sits in the path of a running
script. A worker outage and an api outage are independent failures.

## One request

```mermaid
sequenceDiagram
    participant C as Client
    participant W as Worker
    participant S as Script service
    C->>W: GET /your-script/path
    W->>S: resolve identifier (pointer cache miss only)
    S-->>W: script row + revision id
    W->>W: prepared revision from blob cache
    W->>W: fresh Luau VM, run fetch listener
    W-->>C: response
```

Every request runs in a fresh VM. Nothing survives between requests in
the interpreter; everything durable lives behind a platform surface
(objects, kv, queues).

## Caches

<table>
  <thead>
    <tr><th>Cache</th><th>Maps</th><th>Bounded by</th><th>Staleness cost</th></tr>
  </thead>
  <tbody>
    <tr><td>pointers</td><td>public identifier to script row</td><td>5 s (<code>POINTER_TTL_SECS</code>)</td><td>a publish becomes visible within the TTL</td></tr>
    <tr><td>revisions</td><td>revision id to prepared program</td><td>128 MB (<code>REVISION_CACHE_MB</code>)</td><td>none, revisions are immutable</td></tr>
    <tr><td>blobs</td><td>blake3 hash to bytes</td><td>256 MB (<code>BLOB_CACHE_MB</code>)</td><td>none, content-addressed</td></tr>
  </tbody>
</table>

The caches make the steady state node-local: the script service is
consulted on cache misses, not per request. A worker that has served a
script once keeps serving it through a control-plane outage until the
pointer expires.

## Node membership

```mermaid
sequenceDiagram
    participant W as Worker
    participant R as Placement store
    W->>R: register at boot
    R-->>W: node id, beat every 15 s
    loop every 15 s
        W->>R: heartbeat, with in-flight request count
    end
    alt graceful stop
        W->>R: deregister at the signal (5 s timeout)
    else crash
        Note over R: 45 s of silence (NODE_TTL_SECS): the reaper removes the node
    end
    R->>R: departure record, then every lease the node held is freed
    W->>R: a beat answered NOT_FOUND re-registers
```

Membership is the root fact of the cluster: object leases and alarm
rows hang off it. Every departure, graceful or reaped, writes a record
of what the node held before its leases are freed, which is what the
directory's crash sweep and the placement fence read.
