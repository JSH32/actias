## Declare

```lua
local settle = workflow "settle-sale" (function(wf, input)
    -- run body
    return { outcome = "done" }
end)
```

Referencing one declared elsewhere:

```lua
local settle = workflows "settle-sale"
```

One script per project declares a name; a second declaration is
refused at publish.

## Starting and addressing runs

```lua
local run = settle:start(input, { id = "sale-lot-42" })
local run = settle:get("sale-lot-42")

run.started                 -- true when start created the run
run:signal("paid", { by = "ada" })
run:cancel("no longer needed")
run:status()                -- { kind, seq, at } of the newest journal entry
```

<table>
  <thead>
    <tr><th>Rule</th><th>Refusal</th></tr>
  </thead>
  <tbody>
    <tr><td><code>start</code> takes the input and <code>{'{ id = "…" }'}</code></td><td><code>start takes the input and {'{ id = "..." }'}; the id is the run's identity, so a retried start joins it.</code></td></tr>
    <tr><td>an id is a non-empty string without <code>/</code></td><td><code>A run id is a non-empty string without '/'.</code></td></tr>
  </tbody>
</table>

A deterministic id (`"sale-" .. lot`) lets routes address a run
without a lookup table. `cancel` propagates to every run this one
spawned.

## wf verbs

```lua
wf:step(name, body)
wf:step(name, { retries = 3, backoff = "5s", timeout = "30s" }, body)
wf:sleep(duration)
wf:await(name, { timeout = duration })
wf:race({ "a", "b" }, { timeout = duration })
wf:all({ "a", "b" }, { timeout = duration })
wf:spawn("definition-name", input)
```

<table>
  <thead>
    <tr><th>Verb</th><th>Returns</th></tr>
  </thead>
  <tbody>
    <tr><td><code>step</code></td><td>whatever the body returned, recorded on first run</td></tr>
    <tr><td><code>sleep</code></td><td>nothing, after the duration</td></tr>
    <tr><td><code>await</code></td><td>the signal payload, or <code>nil</code> on timeout</td></tr>
    <tr><td><code>race</code></td><td>payload, name of the first to arrive; <code>nil, nil</code> on timeout. Losers keep running and their signals stay consumable; an empty set is refused</td></tr>
    <tr><td><code>all</code></td><td>payloads in argument order; <code>nil</code> per timed-out entry. The timeout applies to each entry in turn, not to the whole</td></tr>
    <tr><td><code>spawn</code></td><td>a job handle whose completion <code>all</code> and <code>race</code> accept; takes the definition's name, not its handle</td></tr>
  </tbody>
</table>

### wf.step_id

The executing effect's name, for anything outside the platform that
deduplicates: an idempotency key, a row id, an object key.

```lua
wf:step("charge", function()
    return Payments("desk"):charge(sale.price, wf.step_id)
end)
```

The value reads `<run>/<step>#<occurrence>.<try>`, for example
`settle-sale/sale-lot-42/charge#1.1`.

<table>
  <thead>
    <tr><th>Across</th><th>The id</th></tr>
  </thead>
  <tbody>
    <tr><td>a crash between the effect and its recorded result</td><td>stays the same, so the repeat is recognised</td></tr>
    <tr><td>a retry after a recorded failure</td><td>changes, because that attempt is a new effect</td></tr>
    <tr><td>the same step name reached again (a loop)</td><td>changes, because each pass is its own effect</td></tr>
    <tr><td>a replay of an already-recorded step</td><td>never runs the body at all</td></tr>
    <tr><td>outside a step body</td><td>an error: <code>wf.step_id names the effect a step is performing; it exists only inside a step body.</code></td></tr>
  </tbody>
</table>

## Determinism

Run code replays from the journal after every park, crash or deploy.
It must take the same path given the same journal.

<table>
  <thead>
    <tr><th>In run code</th><th>Behaviour</th></tr>
  </thead>
  <tbody>
    <tr><td><code>os.time()</code>, <code>os.clock()</code>, <code>math.random()</code>, <code>uuid.v4()</code></td><td>journaled, replayed identically</td></tr>
    <tr><td><code>secret "name"</code></td><td>pinned to the version the run first resolved</td></tr>
    <tr><td><code>os.date</code>, <code>math.randomseed</code></td><td>refused</td></tr>
    <tr><td>kv, database and object calls outside a step</td><td>refused: <code>not available in workflow code, perform effects inside wf:step</code></td></tr>
    <tr><td><code>http</code>, <code>crypto</code>, <code>Jwt</code></td><td>absent, step bodies included; call an [object](/docs/reference/objects) from a step</td></tr>
  </tbody>
</table>

## Example

```lua
local sales = database "sales" { migrations = "migrations/sales" }
local Account = objects "Account"

local settle = workflow "settle-sale" (function(wf, sale)
    wf:step("notify", { retries = 3 }, function()
        Account(sale.winner):notify("pay-up", { price = sale.price })
    end)

    local _, which = wf:race({ "paid", "cancelled" }, { timeout = "72h" })
    if which ~= "paid" then
        return { outcome = "void" }
    end

    local confirmations = wf:all({ "shipped", "received" }, { timeout = "7d" })
    if confirmations[1] == nil or confirmations[2] == nil then
        return { outcome = "disputed" }
    end

    wf:step("settle", { retries = 3 }, function()
        sales:exec("UPDATE sales SET state = 'settled' WHERE id = ?", { sale.id })
    end)
    return { outcome = "settled" }
end)
```

### Gotchas

- `retries = 3` is three attempts in total.
- Steps do not nest. One effect per step; a `wf:step` inside a step
  body is an error.
- Renaming a step breaks runs already in flight. Replay compares the
  journal against the code it re-executes and fails on a mismatch
  rather than guessing.
- A duplicate signal is safe. An unconsumed extra is set aside instead
  of breaking replay, because buttons get clicked twice.
