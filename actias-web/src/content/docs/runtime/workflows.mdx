## What a workflow is

A workflow is a function that runs like ordinary code but can pause
for days and resume where it stopped, including across crashes and
deploys.

```lua
local settle = workflow "settle-sale" (function(wf, sale)
    wf:step("notify", { retries = 3 }, function()
        Account(sale.winner):notify("pay-up", { price = sale.price })
    end)

    local paid, which = wf:race({ "paid", "cancelled" }, { timeout = "72h" })

    if which ~= "paid" then
        wf:step("void", { retries = 3 }, function()
            db:exec("UPDATE sales SET state = 'void' WHERE id = ?", { sale.id })
        end)
        return { outcome = "void" }
    end

    wf:step("settle", { retries = 3 }, function()
        db:exec("UPDATE sales SET state = 'settled' WHERE id = ?", { sale.id })
    end)

    return { outcome = "settled" }
end)
```

Start a run with an id you choose:

```lua
settle:start({ id = "lot-42", winner = "ada", price = 25 },
    { id = "sale-lot-42" })
```

## Replay

Each step, signal and timer is journaled before it takes effect. A
resuming run replays the function from the top, and steps that already
ran return their recorded results instead of running again.

This requires the run's own code to be deterministic: given the same
journal it must take the same path. Effects belong inside steps.

```lua
-- Wrong: replay can take a different branch
if os.time() % 2 == 0 then ... end

-- Right: the step result is journaled
local now = wf:step("stamp", function() return os.time() end)
if now % 2 == 0 then ... end
```

Workflow environments do not include `http`, `crypto` or `Jwt`, even
inside step bodies. Reach effects by calling an
[object](/docs/runtime/objects) from a step:

```lua
local receipt = wf:step("sign", function()
    return Registrar("desk"):sign(payload)
end)
```

The step records what the object returned, so replay does not sign
again.

## Steps

```lua
wf:step("name", function() ... end)
wf:step("name", { retries = 3, backoff = "5s", timeout = "30s" }, function() ... end)
```

  <thead>
    <tr><th>Option</th><th>Default</th><th>Means</th></tr>
  </thead>
  <tbody>
    <tr><td><code>retries</code></td><td>1</td><td>total attempts, not attempts after the first</td></tr>
    <tr><td><code>backoff</code></td><td>2s</td><td>wait before attempt 2, doubling after that</td></tr>
    <tr><td><code>timeout</code></td><td>none</td><td>how long one attempt may run</td></tr>
  </tbody>
</table>

Step names must be stable across revisions, because replay matches
recorded results to them by name.

When a step exhausts its attempts the run parks as failed and stops
there. The journal keeps everything up to that point, and the console
can resume it.

### Making an effect safe to repeat

A step records its result after the body returns, so a crash in
between leaves the platform unable to know whether the effect
happened. It cannot: that gap belongs to the outside world. What it
can do is tell you the effect's name, so the outside world can
recognise a repeat.

```lua
wf:step("charge", { retries = 3 }, function()
    return http.make_request({
        uri = "https://api.example.com/charges",
        method = "POST",
        headers = { ["Idempotency-Key"] = wf.step_id },
        body = json.encode({ amount = order.total }),
    })
end)
```

`wf.step_id` names the effect the body is performing, and it holds
still exactly where that matters. A run resumed after a crash calls
the body again with the same `wf.step_id`, so a provider keyed on it
returns the original charge instead of making a second one. A retry
after a failure the platform actually recorded gets a new
`wf.step_id`, because that attempt is a new effect and you want it to
go through. So does each pass of a loop: calling the same step name
for every item in an order is one effect per item, and they are named
apart.

The same string works anywhere a repeat needs recognising: a row id,
an object key, a filename. Reading it outside a step body is an
error, since there is no effect to name there.

## Waiting

```lua
wf:sleep("24h")
wf:await("approved", { timeout = "48h" })
wf:race({ "paid", "cancelled" }, { timeout = "72h" })
wf:all({ "shipped", "received" }, { timeout = "7d" })
```

<table>
  <thead>
    <tr><th>Verb</th><th>Returns</th></tr>
  </thead>
  <tbody>
    <tr><td><code>sleep</code></td><td>nothing; resumes after the duration</td></tr>
    <tr><td><code>await</code></td><td>the signal payload, or nil on timeout</td></tr>
    <tr><td><code>race</code></td><td>the payload and the name that arrived first</td></tr>
    <tr><td><code>all</code></td><td>payloads in argument order; a timed-out entry is nil</td></tr>
  </tbody>
</table>

A parked run holds no resources. It is journal rows and a timer.

## Signals

Signals come from outside the run:

```lua
routes["POST /api/sale/pay"] = function(request, body, user)
    settle:get("sale-" .. body.id):signal("paid", { by = user })
    return reply(200, {})
end
```

Run ids are yours to choose, so a route can address a run without a
lookup table.

Duplicate signals are safe. An unconsumed extra is set aside rather
than breaking replay, which matters because buttons get clicked twice.

## Inspecting

The console lists runs with status and current step, shows the journal
as a timeline, and offers resume for failed runs.

## Workflow or queue

If anyone will ask how one specific job is doing, use a workflow: runs
are named, inspectable and signalable, and each carries a journal.

Otherwise use a [queue](/docs/runtime/queues): anonymous, cheap,
retried in bulk. A queue handler can start a workflow when a message
turns out to need one.

### Gotchas

- `retries = 3` is three attempts in total, not one plus three.
- Steps do not nest. One effect per step; a `wf:step` inside a step
  body is an error.
- Renaming a step breaks runs already in flight. Replay compares the
  journal against the code it re-executes, and a mismatch fails the
  run with a journal divergence rather than guessing.
- `http`, `crypto` and `Jwt` are absent from a workflow environment,
  step bodies included. Call an object to reach them.
