## Delivery

<table>
  <thead>
    <tr><th>Surface</th><th>Promise</th><th>What your code must do</th></tr>
  </thead>
  <tbody>
    <tr><td>Object method call</td><td>exactly once, serialized per object</td><td>nothing</td></tr>
    <tr><td>Queue message</td><td>at-least-once</td><td>handler safe to run twice</td></tr>
    <tr><td>Object stream edge</td><td>at-least-once, in order per publisher; a handler that committed never re-runs for the same event</td><td><code>receives</code> handler safe to run twice</td></tr>
    <tr><td>Connection edge</td><td>at-most-once</td><td>client re-reads state on reconnect</td></tr>
    <tr><td>Workflow step</td><td>recorded once, replayed after</td><td>keep run code deterministic</td></tr>
    <tr><td>Alarm</td><td>fires once per set, survives restarts</td><td>nothing</td></tr>
  </tbody>
</table>

At-least-once means a repeat is possible after a machine failure at
the wrong moment. Make repeated work harmless: check an id, use
`INSERT OR IGNORE`, or update conditionally on current state.

Stream edges narrow the window: the follower records the event in the
same transaction as its handler's writes, so a redelivered event is
skipped, not re-run. Keep the handler idempotent anyway; the promise
covers commits, not a crash mid-handler.

At-most-once means loss is possible. Only connection edges promise
this, because a tab can vanish mid-frame. Anything that must survive
belongs on the object one hop back.

## Ordering

Events from one publisher reach one follower in publish order. There
is no ordering promise across different publishers. If order matters
across sources, put a sequence number in the data.

Calls to one object are ordered. Calls to different objects are not.

## Transactions

A method's writes to `state.sql` commit together when the method
returns. A `state:publish` inside the method is part of the same
commit, so an event never describes a write that did not happen.

The answer waits for one thing more than the commit: the writes
leaving the machine. Committing locally and being told it happened
are separate events, and the caller only ever sees the second, which
is what makes the durability promise below true. Calls that arrive
while an answer is waiting still run, so a busy object commits at its
own speed and a burst of writes leaves together.

Migrations apply inside the transaction of the call that triggered
them: a failing migration applies nothing and surfaces as that call's
error.

Workflow steps commit their journal entry with their result. A crash
between two steps replays from the last recorded one.

## Limits

Defaults. Most are operator-tunable on a self-hosted worker; the two
budget rows are constants today.

Guest code is metered in work rather than seconds, so waiting on io,
a database or another object costs nothing and only computation counts.
The clock stays as a backstop for what the meter cannot see: code
blocked inside a host call that never re-enters the vm.

The connection inbox is not a buffer to fill. A connection whose
handlers cannot keep up has chosen to fall behind, and the platform
closes it rather than growing memory on its behalf.

An idle connection hibernates: its vm drops after the idle threshold
and rebuilds for the next item its program declares a handler for,
with `conn.state` intact. A class that declared `event = "forward"`
does not rebuild it for deliveries at all, since the platform writes
those frames. The socket never notices; only the memory does.

## Failure behaviour

A machine leaving gracefully (deploys, scale-downs) loses nothing:
the drain flushes every object's unshipped state before the process
exits. Objects move, alarms re-arm from storage, workflow runs
resume from their journal, queue messages redeliver, and stream
subscriptions survive their follower rehoming.

A hard crash cannot take back a call the platform answered. A method
that wrote is not answered until its writes have reached durable
storage off the machine, so anything you were told succeeded survives
the loss of the node that ran it. What a crash can take back is work
that was never acknowledged: a call still waiting for its answer
(the caller sees the connection fail, which reads as an unknown
outcome, the same as any interrupted request), and platform work with
no caller to answer, such as an alarm handler's writes.

When durable storage is unreachable, writes stop being acknowledged
rather than being acknowledged falsely: the call fails with an unknown
outcome after ten seconds, and the platform keeps trying to store the
write behind it. Reads keep answering throughout. A retry needs the
same idempotence any timed-out request needs, because the first
attempt may still land.

Connections do not survive a machine going away. Clients reconnect and
re-follow; that path runs often enough in normal operation (deploys,
scaling) that it should be part of the client from the start.
